# ЭП: Кошелёк ресурсов — детали реализации

Общий концепт — в `Кошелек ресурсов - концепция.md`. Здесь — что именно изменено и как это устроено технически.

## Эндпоинты бэка (без изменений, `/home/mic/learn/era/eraofchange`)

| Метод | URL | Запрос | Ответ | Источник |
|---|---|---|---|---|
| GET | `/players.json` | — | `[{id, name, identificator, ...}]` | `players_controller.rb#index` |
| GET | `/players/:id/show_players_resources.json` | — | `{ "<identificator>": count, ... }` (только явно заданные ресурсы) | `players_controller.rb#show_players_resources` |
| GET | `/resources/show_all_resources.json` | — | `[{id, name, identificator, country_id, icon, params, ...}]` (может быть несколько строк с одинаковым `identificator` для разных стран — на фронте берётся первое совпадение по `identificator`) | `resources_controller.rb#show_all_resources` |
| POST | `/players/:id/exchange_resources.json` | `{request: {with_whom: "<identificator получателя>", hashed_resources: [{identificator, count, name}]}}` | `{success: true, result: [...]}` или `{success: false, error: "..."}` (422) | `players_controller.rb#exchange_resources` → `Player#exchange_resources` |

`with_whom` — это `identificator` игрока-получателя (строка), а не числовой `id`: бэкенд ищет получателя через `Player.find_by(identificator: with_whom)`.

Иконки ресурсов не запрашиваются с бэка — используется конвенция `/images/resources/{identificator}.png` (уже применяется в `ShowPricesMobile.vue`), файлы лежат в `era_front/public/images/resources`.

## Новые файлы фронтенда (`era_front`)

- `src/stores/walletPlayer.js` — Pinia-стор (composition-API, как `src/stores/caravan.js`). Хранит выбранного игрока `{id, name, identificator}` в state и в `localStorage` под ключом `wallet_player`. Пишет напрямую через `localStorage.getItem/setItem` — **не** через VueUse `useStorage`, он намеренно исключён из автоимпорта в `vite.config.js` (`ignore: ['useCookies', 'useStorage']`). Метода смены игрока нет.
- `src/views/pages/wallet/PlayerSelectMobile.vue` — экран выбора игрока при первом запуске: список из `/players.json`, поиск по имени, диалог подтверждения перед вызовом `walletPlayerStore.setPlayer(...)`.
- `src/views/pages/wallet/WalletMobile.vue` — экран кошеля: `GET show_players_resources` + `GET show_all_resources` (для названий), сетка ресурсов с количеством > 0. `defineExpose({ refresh })` — родитель вызывает `refresh()` после успешной передачи, чтобы обновить баланс без размонтирования компонента.
- `src/views/pages/wallet/TransferRecipientMobile.vue` — шаг «Кому»: список игроков из `/players.json` без текущего игрока.
- `src/views/pages/wallet/TransferBasketMobile.vue` — шаг «Корзина»: заново запрашивает баланс и каталог ресурсов (свежие данные на момент сборки корзины), количество ограничено `available` на клиенте (финальную проверку остатков всё равно делает бэкенд в `Player#validate_resources_availability`).
  - Количество — редактируемый `<input type="number">` (не текст), значение клэмпится в `setCount()` на каждый `input`/`blur` (пусто/не число → 0, за пределы `[0, available]` — обрезается).
  - Кнопки +/- реагируют на `@pointerdown`/`@pointerup`/`@pointerleave`/`@pointercancel` (не `@click`): нажатие сразу делает один шаг, при удержании дольше `HOLD_INITIAL_DELAY` (400 мс) запускается авто-повтор через рекурсивный `setTimeout`, интервал между шагами уменьшается на `HOLD_ACCELERATION_STEP` (25 мс) на каждом шаге от `HOLD_REPEAT_START_DELAY` (220 мс) до пола `MIN_HOLD_DELAY` (40 мс) — число «бежит» с ускорением. Состояние удержания — `Map` по `item.identificator` (не `WeakMap`, т.к. нужно перебором очистить все таймеры в `onBeforeUnmount`). Автоповтор сам останавливается, как только упирается в границу `[0, available]` (шаг не меняет значение → `stopHold`).
- `src/views/pages/wallet/TransferConfirmMobile.vue` — шаг подтверждения: `POST exchange_resources`, обработка `success:false`/422 с показом текста ошибки без сброса корзины.
- `src/views/pages/wallet/WalletFlow.vue` — оркестратор шагов кошеля (`currentScreen`: wallet → recipient → basket → confirm), пробрасывает `player` пропом во все подэкраны. `handleBack()` (вызывается родителем `MobileHelper.vue` по аппаратной кнопке "назад") пошагово откатывает `currentScreen`, а не управляет `history`/`popstate` сам — так же, как это устроено у `ExchangeMobile.vue` (единственный слушатель `popstate` — в `MobileHelper.vue`, дочерние компоненты только реализуют `handleBack()`).
- `src/sw.js` — кастомный service worker для `vite-plugin-pwa` (`strategies: 'injectManifest'`):
  ```js
  import { cleanupOutdatedCaches, precacheAndRoute } from 'workbox-precaching'
  cleanupOutdatedCaches()
  precacheAndRoute(self.__WB_MANIFEST)
  self.skipWaiting()
  self.addEventListener('activate', () => self.clients.claim())
  ```
  Никакого `registerRoute` для API нет — прекэшируются только билд-ассеты из `self.__WB_MANIFEST`, запросы к `${VITE_PROXY}/...` под перехват не попадают, баланс ресурсов всегда живой.
- `public/manifest.webmanifest` — веб-манифест написан вручную (не генерируется плагином, см. ниже почему). `start_url: "/"` — рассчитан на деплой на `calc.igroteh.su`, где приложение отдаётся с корня домена (см. раздел «Деплой» ниже).
- `public/pwa-192x192.png`, `public/pwa-512x512.png` — иконки манифеста, сгенерированы из `public/logo.png` (`convert ... -resize 512x512 -background white -gravity center -extent 512x512`).
- `src/stores/pwaInstall.js` — Pinia-стор с одним полем `deferredPrompt` (`shallowRef`, чтобы не заворачивать нативный `BeforeInstallPromptEvent` в глубокий реактивный прокси) и методами `setDeferredPrompt`/`clearDeferredPrompt`.
- `src/views/pages/PwaInstallBanner.vue` — плашка «Установить приложение», зафиксирована сверху экрана (`position: fixed; top: 0`), т.к. низ экрана везде занят плавающими кнопками действий. Видна на любом экране приложения (в т.ч. до выбора игрока), пока `pwaInstallStore.deferredPrompt` не пуст и плашку не закрыли крестиком. По клику «Установить» — `event.prompt()` → `await event.userChoice` → `clearDeferredPrompt()`.

## Изменённые файлы

- `vite.config.js` — добавлен `VitePWA({ strategies: 'injectManifest', srcDir: 'src', filename: 'sw.js', injectRegister: false, manifest: false, injectManifest: { injectionPoint: 'self.__WB_MANIFEST', globIgnores: ['index.html', 'noble_helper.html'] } })`.
  - **`manifest: false`** — важно: `vite-plugin-pwa` в multi-page сборке (у нас 3 HTML-входа: `index.html`, `merchant_mobile_helper.html`, `noble_helper.html`) инжектит `<link rel="manifest">` во **все** HTML-файлы разом, независимо от `injectRegister`. Своего способа ограничить это одним входом у плагина нет. Поэтому автогенерация манифеста отключена, а `<link rel="manifest">` прописан вручную только в `merchant_mobile_helper.html`, а сам файл манифеста — статика в `public/`.
  - **`globIgnores: ['index.html', 'noble_helper.html']`** — по умолчанию `precacheAndRoute` в `injectManifest`-режиме прекэширует вообще все файлы в `dist/` (это отдельный механизм от инжекта ссылки на манифест, регулируется через `workbox-build`). Без этого исключения service worker, единожды зарегистрированный со страницы кошеля (scope `/`), стал бы перехватывать навигацию на `/` (админка) и `/noble_helper.html` и отдавать их закэшированную HTML-страницу — некорректно для несвязанных приложений на том же домене. Хэшированные JS/CSS-чанки (в т.ч. те, что относятся к `index`/`noble` записям сборки) в прекэш всё равно попадают, но это безопасно: имя файла = хэш содержимого, отдача такого файла из кэша SW побайтово идентична сетевому ответу.
  - Проверено сборкой (`pnpm build`): `dist/merchant_mobile_helper.html` содержит ровно один `<link rel="manifest">`, `dist/index.html` и `dist/noble_helper.html` — ни одного; в манифесте прекэша (`dist/sw.js`) нет записей `index.html`/`noble_helper.html`.
- `src/mobile-entry.js` — добавлена регистрация SW **только здесь** (не в `main.js` админки, не в `noble-entry.js`):
  ```js
  if ('serviceWorker' in navigator) {
    window.addEventListener('load', () => navigator.serviceWorker.register('/sw.js'))
  }
  ```
  Здесь же — перехват `beforeinstallprompt`/`appinstalled` в `pwaInstallStore` (стор создаётся через `usePwaInstallStore(pinia)` с явной передачей инстанса `pinia`, т.к. слушатель регистрируется до `app.mount()` вне контекста компонента):
  ```js
  const pwaInstallStore = usePwaInstallStore(pinia)
  window.addEventListener('beforeinstallprompt', (event) => {
    event.preventDefault()
    pwaInstallStore.setDeferredPrompt(event)
  })
  window.addEventListener('appinstalled', () => pwaInstallStore.clearDeferredPrompt())
  ```
- `merchant_mobile_helper.html` — заголовок → «ЭП: Кошелёк ресурсов», добавлены `<link rel="manifest">`, `<meta name="theme-color">`, `<link rel="apple-touch-icon">`.
- `src/views/pages/MobileHelper.vue`:
  - гейт по `useWalletPlayerStore().hasPlayer`: пока `false` — рендерится только `PlayerSelectMobile`, остальная разметка (меню + все экраны) обёрнута в `<template v-else>`;
  - заголовок меню → «ЭП: Кошелёк ресурсов»;
  - 4-я плитка меню «Кошель» → `currentScreen = 'wallet'` → `<WalletFlow :player="walletPlayerStore.player" @back="backToMenu" />`, добавлена в `componentRefs` наравне с `caravan`/`production`/`prices` для обработки аппаратной кнопки "назад".
- `package.json` / `pnpm-lock.yaml` — добавлены `devDependencies`: `vite-plugin-pwa`, `workbox-precaching` (нужен для сборки кастомного `src/sw.js` в режиме `injectManifest` — без него сборка падает: `Rollup failed to resolve import "workbox-precaching"`).

## Иконки MDI

В проекте иконки собираются билд-скриптом `src/plugins/iconify/build-icons.js` (`pnpm run build:icons`, также запускается автоматически через `postinstall`) в один файл `src/plugins/iconify/icons.css` — CSS-классы вида `.ri-xxx { --svg: url(...) }` + общее правило с `mask-image: var(--svg); background-color: currentColor`. До этой правки в сборку попадал только набор Remix Icon (`@iconify-json/ri`) и несколько логотипов (`@iconify-json/bxl`) — из-за этого ни один `<VIcon icon="mdi-...">` по всему проекту (не только в кошельке) не отображался: класс `mdi-xxx` навешивался на элемент, но для него не было CSS-правила.

Добавлено:
- Зависимость `@iconify-json/mdi` (devDependencies).
- В `build-icons.js` — источник `@iconify-json/mdi/icons.json` с явным списком иконок (тот же паттерн, что уже используется для `bxl`: не весь набор MDI, а перечисленные иконки). Список составлен по всем `mdi-*`, реально используемым в проекте (`grep -rohE "mdi-[a-z0-9-]+" src/`), чтобы не раздувать CSS полным набором Material Design Icons (7000+ иконок).
- Если в проекте появится новая иконка `mdi-что-то-ещё` — её нужно добавить в список `icons` для mdi в `build-icons.js` и перезапустить `pnpm run build:icons`, иначе класс будет навешен, но не отрисуется (то же самое уже верно для `bxl`).

## Деплой (`era_scripts/deploy-frontend.sh`, отдельный репозиторий)

`calc.igroteh.su` обслуживается не из общей сборки `era_front` (`/opt/era/era_front/current`), а из отдельного каталога `/opt/era/mer_calc/current`, который деплой-скрипт наполняет так: собирает весь `pnpm build`, затем копирует из `dist/` только `merchant_mobile_helper.html` (переименовывая в `index.html`), `assets/`, `images/`, `favicon.ico`, `loader.css`, `logo.png` — остальные файлы `dist/` игнорируются.

До этой доработки скрипт не копировал `manifest.webmanifest`, `sw.js`, `pwa-192x192.png`, `pwa-512x512.png` — на `calc.igroteh.su` они отдавали бы 404, приложение не проходило бы критерии установимости, и `beforeinstallprompt` никогда бы не сработал. Добавлено копирование этих четырёх файлов в блок сборки mobile helper (аналогично `favicon.ico`/`logo.png`).

## Формат данных в localStorage

Ключ `wallet_player`, значение — JSON:
```json
{ "id": 1, "name": "Тестовый Иван", "identificator": "ivan_test" }
```

## Как проверялось

1. `pnpm build` — чистая сборка, проверено содержимое `dist/` (см. выше про манифест и прекэш).
2. Полный сценарий прогнан headless Chrome (CDP) поверх `pnpm dev` с `VITE_PROXY`, временно указанным на локальный mock-бэкенд (без сети до продакшена и без риска что-то сломать в реальной игре):
   выбор игрока → сохранение в `localStorage` → главное меню (плитка «Кошель») → кошель (Золото 50 / Лес 12 / Лошади 3) → «Передать» → выбор получателя → корзина (+2 к золоту, ограничение по `available` проверено) → подтверждение → `POST exchange_resources` с телом
   `{"request":{"with_whom":"maria_test","hashed_resources":[{"identificator":"gold","name":"Золото","count":2}]}}` (в точности совпадает с контрактом бэкенда) → баланс на экране кошеля обновился (Золото 48).
3. Против реального прод-бэкенда (`https://epoha.igroteh.su/backend`) проверены только read-only эндпоинты (`players.json` через `curl`) — мутирующий `exchange_resources` намеренно не запускался на живых данных игры.
4. Плашка установки проверена тем же headless Chrome: на страницу отправлялось синтетическое событие `beforeinstallprompt` (с подставными `prompt()`/`userChoice`, т.к. реальные heuristics установимости Chrome headless не воспроизводит) — плашка появляется поверх любого экрана (в т.ч. до выбора игрока), клик «Установить» вызывает `event.prompt()`, после `userChoice` плашка скрывается.
5. Настоящий прогон полных критериев установимости (реальный `beforeinstallprompt` от Chrome, а не синтетический) и офлайн-открытие через установленный на телефон значок — не проверялись в этой сессии, это стоит перепроверить вручную после деплоя на `calc.igroteh.su`.
6. После добавления MDI-иконок, инпута количества и ускоряющегося автоповтора — прогнан тот же headless-сценарий: скриншотами подтверждено, что иконки (стрелки в меню, плюс/минус/крестик в корзине, установка) теперь рендерятся; ручной ввод числа в поле (программный `HTMLInputElement.value` + событие `input`) корректно обновляет состояние; реальные события мыши (`Input.dispatchMouseEvent` в CDP, не синтетический JS-event) на кнопке «+» с зажатием на ~2 секунды дали замеры `1→2→3→5→9→15→22→28` — то есть шаг ускоряется, а после `mouseReleased` число дальше не меняется (таймеры корректно останавливаются, утечки/убегания нет).
